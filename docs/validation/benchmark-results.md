# Foundation Benchmark Results

Run date: 2026-10-19

## Status

This validation-prototype report is accepted for implementation planning under the explicit user-approved scope exception recorded in `foundation-baseline.md`. Initial observations were run in the Codex in-app browser on the local Apple M4 Mac mini. Additional observations were captured in Microsoft Edge 152.0.4191.53 on the same host. The Edge UA reports `Edg/152.0.0.0`; its release channel was not independently verified. The Edge viewport measured 1557x1456 CSS pixels at device pixel ratio 2. It does not establish coverage of the 1920x1080 minimum or 2560x1440 recommended reference display profiles. Chrome, Firefox, and a minimum-tier device remain untested.

The measurements below establish that the prototype and chosen Three.js/glTF APIs work on representative data. They are not cross-browser performance compliance evidence. The numeric targets are provisional implementation-planning budgets; release verification must collect the missing coverage and confirm or revise them.

## Candidate Budgets for Review

These are provisionally accepted MVP planning targets under the documented scope exception. They are not demonstrated pass thresholds. Review them against measurements on both reference tiers and all latest-stable supported browser families before release.

| Metric                      | Candidate target                                                               | Measurement definition                                                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Pointer-to-visible feedback | p95 <= 50 ms                                                                   | Last pointer input event to the first animation frame that renders its resulting viewport state; at least 200 samples after warm-up.                                                 |
| Common command duration     | p95 <= 50 ms                                                                   | Synchronous document mutation for primitive transform, component transform, and common eligible mesh operation; exclude UI framework rendering and report each operation separately. |
| Viewport responsiveness     | p95 frame interval <= 33.3 ms on minimum tier and <= 20 ms on recommended tier | At least 60 seconds while navigating each representative scene; report frame interval distribution and missed frames.                                                                |
| Memory                      | <= 1 GiB renderer + application attributable working set on minimum tier       | Must use browser/process profiling that separates or explicitly accounts for JS heap, GPU allocations, and native memory; do not substitute `performance.memory` alone.              |
| File import/export          | 128x128 mesh GLB import and export each p95 <= 1 s                             | At least 30 runs per operation, with warm/cold results and exact file byte size. Add the 100-object scene and native project once its format exists.                                 |

If either device tier cannot meet a candidate target, record the failing browser/device/scene and review the target and product scope explicitly; do not mask a failure by silently lowering fixture sizes.

## Repeatable Procedure

1. Start the loopback-only allowlist server with `node tests/prototypes/foundation-benchmark/server.mjs`.
2. Use a fresh browser profile or close unrelated heavy tabs. Set the device display to the tier's target resolution and record OS scaling, browser build/channel, OS, CPU, memory, GPU, and graphics runtime.
3. Load `http://127.0.0.1:4173/`, wait 10 seconds for shader compilation and warm-up, then select each fixture and leave the browser foregrounded.
4. Run at least 30 batches for command and file operations; collect at least 200 pointer samples and 60 seconds of viewport frame samples per fixture. Export the JSON report after each device/browser/fixture combination.
5. For memory, capture browser process and GPU memory through the browser's profiling tools before scene load, after warm-up, at peak operation, and after release/garbage collection. Keep JS heap and renderer object counts as diagnostics, not substitutes.
6. Repeat on minimum and recommended device tiers using latest stable Chrome, Edge, Firefox, and Safari. Record failures and unsupported APIs separately.

## Harness Limitations

- The in-browser harness currently uses fixed CDN imports for Three.js 0.186.1. Network/cache state can affect cold-start measurements; bundle size is not yet measured.
- The current report is exploratory and does not automate browser launch, repeatable interaction, device configuration, or aggregation across page reloads.
- Pointer samples use automation-driven dragging and are not physical mouse/trackpad latency.
- The GLB test uses Three.js `GLTFExporter`/`GLTFLoader` only; it does not establish the glTF-Transform decision or native project format performance.
- `renderer.info` geometry/texture counts are object counts, not memory sizes.
- The browser's JavaScript heap metric is optional, engine-specific, and not total application memory.

## Workspace Profiling (Task 5.7)

Run date: 2026-10-20

The production `buildDocumentProjection` path and a full `object.setTransform` command were profiled with Vite+ Vitest on the available Mac mini Apple M4 host (10 CPU cores, 24 GB unified memory, macOS 15.8.1). The runtime was Node.js 24 under the Vite+ test runner (`navigator.platform` reported `MacIntel`, hardware concurrency 10); this isolates synchronous document/projection work but is not a browser WebGL frame or memory measurement. All samples were collected in the same session with 5 warm-up runs followed by 30 timed runs. Projection timing includes document-to-Three.js scene construction and CPU geometry/normal generation, then disposes generated GPU resources; it does not include an actual GPU draw.

| Scenario                                                              |                          Before optimization median / p95 | After optimization median / p95 | Result                                                                                                     |
| --------------------------------------------------------------------- | --------------------------------------------------------: | ------------------------------: | ---------------------------------------------------------------------------------------------------------- |
| 100-box scene projection                                              | Not comparable: initial profile used 100 one-quad objects |                1.298 / 2.238 ms | Current profile uses 100 actual box meshes (800 vertices, 600 faces).                                      |
| 16x16 quad projection (289 vertices, 256 faces)                       |                                          0.255 / 0.329 ms |                0.217 / 0.417 ms | No meaningful change claimed at this size.                                                                 |
| 128x128 quad projection (16,641 vertices, 16,384 faces)               |                                        12.786 / 16.619 ms |              11.413 / 16.607 ms | Median of three isolated runs; typical duration improved about 10.7%, while p95 is effectively unchanged.  |
| `object.setTransform` in a 100-box document (800 vertices, 600 faces) |                          Not measured before optimization |                2.278 / 2.447 ms | Local p95 is below the provisional 50 ms target; three isolated post-change p95 samples were 2.45-2.79 ms. |

The measured hot path was polygon triangulation during projection construction. Triangles now bypass general polygon triangulation; planar convex quads use a deterministic two-triangle fan. Concave and non-planar polygons continue through Three.js `ShapeUtils.triangulateShape`. No worker, WASM, or alternate renderer was introduced because the measurements did not justify that added complexity. Regression tests preserve concave/non-planar triangulation and verify the dense fixture still projects exactly two triangles per quad (98,304 indices total). The optimization reduced median CPU projection-build time in the dense fixture; these samples do not demonstrate a p95 improvement.

Reproduce the isolated profile with:

```sh
OPEN3D_RUN_PROFILE=1 pnpm exec vp test run apps/web/src/workspace/performance.test.ts --reporter=verbose --silent=false
```

The isolated before/after values are directional evidence, not a cross-browser budget pass. No supported-browser 60-second frame-interval run, physical pointer latency run, minimum-tier run, or app-attributable peak-memory profile was collected for this task. Those measurements remain release requirements under the accepted foundation scope exception; the Node projection time must not be substituted for the browser viewport frame budget.
